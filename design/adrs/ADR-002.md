## Context
Developers switch branches frequently. Maintaining separate document copies for every branch causes extreme vector explosion, repetitive heavy embedding calculations on GPU/CPU, and substantial disk waste.

## Evaluated Alternatives
- **Branch-Prefixed File Keys:** Storing separate full indexes per branch (e.g., `main::src/index.ts` vs `dev::src/index.ts`). Rejected: 95%+ of code is identical across branches, wasting massive disk space and duplicating expensive model embedding operations.
- **Single Flat Table with Branch Array:** Storing a `branches: string[]` column on each file/chunk row. Rejected: mutating an array column across thousands of records on every branch switch or rebase creates write amplification and locking contention in LanceDB.
- **3-Table CAS without Branch Pointers:** Storing file versions and chunks without an explicit branch mapping table. Rejected: makes it impossible to query the exact file set present on a specific branch or to handle file deletions on one branch without breaking another.

## Decision
Implement a 4-table Content-Addressable Storage (CAS) architecture:
1. `branch_mapping`: Mutable pointer resolving `(branch, projectId, uri)` to active `fileVersionId`.
2. `file_mapping`: Content-addressable file versions (`fileVersionId = ${uri}::${contentHash}`).
3. `chunk_mapping`: Structural chunk-sequence mapping (`fileVersionId` -> `chunkIndex` -> `chunkHash`).
4. `chunks_pool`: Global deduplicated vector repository (`chunkHash` -> vector, text).

## Consequences
- Deduplication is guaranteed across any number of branches.
- Branch switches and branch creations execute in milliseconds with zero embedding computation for unchanged files.
- File deletions on a branch simply delete the pointer in `branch_mapping`.
- Stale or deleted branches can be pruned cleanly with `DELETE FROM branch_mapping WHERE branch = ?` without corrupting other branch states.

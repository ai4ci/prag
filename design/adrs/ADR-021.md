## Context
`background-worker-queue.md` calls the ingestion queue "thread-safe" in its title, overview and task, but the JavaScript runtime is single-threaded, so the phrase committed to nothing. The decision matters concretely: the daemon must answer `/search` inside a 100ms interactive budget (ADR-005) *while* indexing is running, and anything that blocks the event loop blocks the request path.

Where the time actually goes, in descending cost:
- **ONNX inference** — an async native call. `onnxruntime-node` dispatches `session.run()` onto libuv's threadpool rather than the JS event loop, so the single most expensive operation is most likely already off the main thread without any workers. *This is an assumption, not a measurement* — `toolchain-spike-native-addons.md` is required to confirm it under the chosen runtime (ADR-020).
- **Tree-sitter parsing** — synchronous, whether via native binding or WASM. A large file is a visible stall.
- **Tokenization, whitespace normalization, chunk hashing, vectorised-unit windowing** — synchronous JS, proportional to file size.
- **LanceDB writes** — async native.

So the blocking risk is the *synchronous* parse-and-hash work, not inference. That inverts the usual reason for reaching for a worker pool and narrows what belongs in one.

## Decision
1. **Workers parse; the main thread embeds and writes.** A `worker_threads` pool in `@prag/daemon` owns: reading the file, Tree-sitter / LiteParse parsing, chunk boundary detection, whitespace normalization (ADR-010), `chunkHash` computation, and vectorised-unit windowing (ADR-014). It returns plain chunk records — text, hash, unit boundaries, scope annotation — and nothing else.
2. **The main thread keeps HTTP/MCP serving, ONNX embedding, and every LanceDB write.** No worker ever opens a table. ADR-005's single-writer invariant is therefore preserved *structurally*, not by convention.
3. **`ingestion.workerPoolSize` defaults to 1.** One worker is enough to keep synchronous parsing off the request path, which is the actual problem. Parallelism across cores becomes a config change once it has been measured to be needed, not an assumption baked into the architecture on day one.
4. **Never embed inside a worker.** Model weights are ~130MB per worker (ADR-006); four workers is half a gigabyte of resident memory for a background utility on a developer workstation. Embedding stays on the main thread where exactly one copy of the model is hot.
5. **Transfer, don't copy.** Vectors and large text buffers cross the thread boundary as transferable `ArrayBuffer`/`Float32Array` where the runtime supports it.
6. **Crash isolation is deferred, and scoped to LiteParse if it is ever needed.** Document parsing on a malformed PDF is the most plausible way to take the daemon down. If that proves real in practice, isolating *that one parser* in a child process is the targeted fix — not moving the whole ingestion pipeline out of process.

## Evaluated Alternatives Ruled Out
- **Single-threaded async queue with `setImmediate` yielding between files:** genuinely adequate if inference is already off-loop, and simpler. Rejected as the stated design only because a single large file still stalls the request path mid-parse and no amount of yielding between files fixes that. Pool size 1 is one config value away from this, so little is lost if the measurement says otherwise.
- **Workers that also embed:** full parallel inference, at ~130MB of weights per worker. Rejected on memory footprint alone for a tool that is meant to sit quietly in the background.
- **A child process for all ingestion:** real crash isolation and a memory cap, but it breaks the single-writer invariant unless every write is piped back to the parent, adds IPC serialization of all chunk text, and introduces a second process into lifecycle management — which directly complicates ADR-019's `PRAG_NO_SPAWN` and orphan reaping in the test harness.

## Consequences
- Synchronous parsing cannot stall `/search`, which is what the 100ms budget needs.
- Exactly one copy of the embedding model is resident, regardless of pool size.
- The single-writer property is enforced by structure: workers have no database handle to misuse.
- The pool-size default is deliberately conservative; `toolchain-spike-native-addons.md` must record the measured cost of a parse, an embedding pass and a vector query before anyone raises it.
- If the spike finds that inference *does* block the event loop under the chosen runtime, this ADR is revisited — the conclusion changes, because then the expensive work also needs moving.

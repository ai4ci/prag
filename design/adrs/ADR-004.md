## Context
Storing only float vectors and reference paths saves database space but introduces breaking sync issues if an IDE updates a file or changes branches before a query runs.

## Decision
Store the raw text segment content inside the local database alongside the vector arrays in `chunks_pool.text`.

## Consequences
Because data stays fully local, retaining the text string preserves search speed and query execution reliability without adding privacy concerns. The system can immediately show matching code or documentation blocks, even if the user's workspace is mid-refactor.

## Evaluated Alternatives Ruled Out
### Pure Vector Indexes (No Local Content Retention)
- **What it is:** Storing only generated float vectors and source file path pointers inside the database, reading the live file on disk when a result is fetched.
- **Why considered:** Reduces database disk space and limits potential local privacy footprints.
- **Why ruled out:** Causes major synchronization errors in environments with high file churn. If a developer edits a file or switches branches mid-task, the file state on disk immediately diverges from the version used to calculate the historical vector inside the database.
- **The prag Shift:** Storing raw text chunks directly inside LanceDB alongside vector arrays. Running locally creates zero extra privacy risks while guaranteeing search queries always return the exact code block that matches the semantic vector.

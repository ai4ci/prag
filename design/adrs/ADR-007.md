## Context
Developers querying source code repositories perform two distinct types of queries:
1. **Conceptual semantic queries:** e.g., *"how does the daemon debounce file events"*, which require semantic embedding vectors to match meaning across varying vocabulary.
2. **Exact lexical queries:** e.g., exact function names (`enqueueFileEvent`), interfaces (`SearchHitResult`), configuration keys, error strings, or file paths.

Pure dense vector embeddings frequently struggle with exact alphanumeric symbol matching and rare identifiers, while pure BM25 lexical search misses conceptual queries with differing vocabulary.

## Decision
Implement Hybrid Search from the outset across CLI and MCP interfaces using LanceDB's built-in FTS and vector search capabilities:
1. **Full-Text Indexing (FTS):** Create a BM25 inverted index on the `text` field in `chunks_pool`.
2. **Hybrid Query Execution:** On receiving a search query, the daemon executes both:
   - Dense vector similarity search (cosine distance against `vector` embedding).
   - BM25 full-text search against `text`.
3. **Score Merging (RRF):** Combine the two result sets using Reciprocal Rank Fusion (RRF) with default parameter $k = 60$:
   $$RRF(d) = \sum_{m \in \{dense, bm25\}} \frac{1}{k + rank_m(d)}$$
4. **Metadata Filtering:** Enforce `projectId` and `branch` filtering across both search modalities before or during rank fusion.

## Evaluated Alternatives Ruled Out
- **Pure Dense Vector Search:**
  - *Why considered:* Simpler implementation, requires only vector indexes.
  - *Why ruled out:* Fails frequently on exact code symbol, identifier, or class searches.
- **Pure BM25 / Keyword Search:**
  - *Why considered:* Fast and lightweight without neural models.
  - *Why ruled out:* Defeats the primary purpose of semantic code search and conceptual exploration.
- **External Search Engine (e.g. Meilisearch, SQLite FTS5 alongside LanceDB):**
  - *Why considered:* Mature standalone search engines.
  - *Why ruled out:* Unnecessary operational complexity; LanceDB provides native FTS and hybrid search built directly on Apache Arrow and Tantivy.

## Consequences
- Searches match both natural language concepts and exact code identifiers with high precision.
- Zero extra external search service dependencies; fully self-contained in LanceDB.
- `chunks_pool` requires an FTS index alongside vector storage.

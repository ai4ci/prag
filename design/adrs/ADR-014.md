## Context
The default embedding model (`Xenova/bge-small-en-v1.5`) truncates at 512 tokens (384-dim output); other configurable models have their own ceilings (e.g. `nomic-embed-text` is served by Ollama at a default `num_ctx` of 2048 despite an 8192 upstream maximum). Tree-sitter structural units — a large function, a God-class method — routinely exceed these limits. `syntax-aware-chunking.md` previously had no size bound, so oversized nodes were silently truncated by the tokenizer at embedding time, discarding exactly the back half of the largest, often hardest-to-search code.

## Decision
1. Introduce `embedding.maxChunkTokens` (default 400 — comfortably under the default model's 512-token ceiling) and `embedding.chunkOverlapTokens` (default 60, ~15%) in `config.json`.
2. When a Tree-sitter structural unit exceeds `maxChunkTokens` (measured with the active model's tokenizer), split it into sequential sliding-window sub-chunks of that size with the configured overlap.
3. Each sub-chunk is a distinct `chunk_mapping` row sharing the parent `fileVersionId`, occupying consecutive `chunkIndex` values (e.g. a function spanning indices 12–14 instead of a single index 12).
4. Each sub-chunk's text is prefixed with the same enclosing namespace/class/parent-scope annotation already defined for ordinary chunks, so it remains independently meaningful in vector space.
5. `chunkHash` (per ADR-010's whitespace-normalized hashing) is computed per sub-chunk; identical sub-chunks still dedupe normally via `chunks_pool`.
6. Nodes at or under the limit are unaffected — this only activates for oversized units.

## Evaluated Alternatives Ruled Out
- **Silent truncation:** Simplest, but discards the back half of exactly the chunks most in need of good search.
- **Recursive AST subdivision (descend into child statements/blocks):** Preserves structure slightly better than fixed windows, but needs per-grammar logic for "what is a valid sub-boundary," which is meaningfully more implementation work than a generic token-window splitter and isn't justified yet.
- **Dense-search opt-out for oversized chunks (BM25-only):** Cheap, but removes semantic search specifically for the largest/legacy functions where it's often needed most.

## Consequences
- No information loss for large functions/classes; retrieval granularity actually improves (a large function can surface the specific internal section that matched).
- More `chunk_mapping` rows per oversized unit; marginally less storage efficiency for very large generated files, judged acceptable.
- `syntax-aware-chunking.md`, `daemon-parser-router.md`, and the `chunk_mapping` spec are updated to describe sub-chunking.

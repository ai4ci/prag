## Context
The default embedding model (`Xenova/bge-small-en-v1.5`) truncates at 512 tokens (384-dim output); other configurable models have their own ceilings (e.g. `nomic-embed-text` is served by Ollama at a default `num_ctx` of 2048 despite an 8192 upstream maximum). Tree-sitter structural units — a large function, a God-class method — routinely exceed these limits. `syntax-aware-chunking.md` previously had no size bound, so oversized nodes were silently truncated by the tokenizer at embedding time, discarding exactly the back half of the largest, often hardest-to-search code.

An earlier draft of this ADR fixed truncation by splitting an oversized node into several *chunks*. That conflated two different things: the structural unit a user wants returned, and the token window a model can actually consume. It also fragmented BM25 scoring across pieces of one function and made a single large function surface as several competing hits.

## Decision
Separate the two concepts explicitly.

1. **Definitions:**
   - A **chunk** is one complete structural unit (a Tree-sitter node per ADR-003, or a layout block for documents). It is the unit of retrieval, of `chunk_mapping` ordering, and of content-addressable dedup. `chunkHash` is the SHA-1 of its whole whitespace-normalized text (ADR-010) **regardless of size** — a chunk is never split for hashing or for return.
   - A **vectorised unit** is a sliding window over a single chunk's text, sized to fit the active model. One chunk yields **1..\* vectorised units** — exactly one when the chunk already fits.
2. **Window configuration:** `embedding.maxVectorUnitTokens` (default 400, comfortably under the default model's 512-token ceiling) and `embedding.vectorUnitOverlapTokens` (default 60, ~15%), measured with the active model's tokenizer. A chunk at or under the limit produces a single vectorised unit covering the whole chunk.
3. **Startup validation:** the daemon reads the active model's reported maximum sequence length and refuses to start if `maxVectorUnitTokens` exceeds it, rather than letting a config change silently reintroduce truncation. The pinned value is recorded in the embedding sidecar (ADR-015).
4. **Data model:** `chunks_pool` keeps `chunkHash` (PK) and `text` (the whole chunk, the BM25 FTS target) and **no longer carries a vector column**. A new `vector_pool` table holds `(chunkHash FK, unitIndex, vector)` with composite key `(chunkHash, unitIndex)`. `chunk_mapping` is unchanged: still exactly one row per chunk.
5. **Scope annotation:** each vectorised unit is prefixed with the chunk's enclosing namespace/class/parent-scope annotation before embedding, so a window from the middle of a large function stays meaningful in vector space. The prefix is an embedding-time construct and is not stored.
6. **Search:** dense search scores `vector_pool`, then collapses to the best-scoring unit per `chunkHash`. From that point the **chunk** is the unit of ranking, fusion and return, so one large function surfaces once. RRF fuses that dense rank against BM25 over `chunks_pool.text` (ADR-007).
7. **Dedup:** unchanged and strengthened — an identical chunk produces the same `chunkHash`, so its vectorised units already exist in `vector_pool` and no embedding work is done, whatever the chunk's size.

## Evaluated Alternatives Ruled Out
- **Multiple chunks per oversized node (the earlier draft):** splits one structural unit across several `chunk_mapping` rows, fragments BM25 scoring, and returns the same function as several competing hits.
- **Silent truncation:** simplest, but discards the back half of exactly the chunks most in need of good search.
- **Recursive AST subdivision (descend into child statements/blocks):** preserves structure slightly better than fixed windows, but needs per-grammar logic for "what is a valid sub-boundary," which is meaningfully more implementation work than a generic token-window splitter and isn't justified yet.
- **Dense-search opt-out for oversized chunks (BM25-only):** cheap, but removes semantic search specifically for the largest/legacy functions where it's often needed most.

## Consequences
- No information loss for large functions/classes, and retrieval granularity improves within a chunk (the best-matching internal window drives the chunk's score) without fragmenting the result.
- The storage schema grows from six to seven tables; this extends the CAS model of ADR-002 rather than replacing it.
- `vector_pool` holds one row per chunk plus extra rows only for oversized chunks.
- `chunks_pool` GC must cascade to `vector_pool` (ADR-017).
- `syntax-aware-chunking.md`, `layout-preserving-chunking.md`, `daemon-parser-router.md`, `storage-schema.md`, and the hybrid-search task are updated for the chunk / vectorised-unit split.

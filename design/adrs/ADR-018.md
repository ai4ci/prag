## Context
A single search command/tool with an optional `projectId` leaves the local-vs-cross-project default ambiguous and gives no natural seam for later restricting broader access — e.g. a shared daemon might want to let a given agent search only the current workspace, never the whole machine's index.

## Decision
1. Replace the single `prag search` CLI command with two explicit commands:
   - `prag search-local <query>`: resolves `projectId` from the current working directory (the same git-root-walk already used for branch auto-detection) and searches only that project. This is the default/primary day-to-day command.
   - `prag search-all <query>`: omits `projectId`, searching across every registered project. Same `--branch`/`--limit`/`--mode`/`--json` options apply to both.
2. Replace the single `semantic_repository_search` MCP tool with two tools, `search_local` and `search_all`, mirroring the CLI split. Both still call the daemon's existing `POST /search` — `search_local` requires/derives a `projectId`, `search_all` omits it. No new daemon HTTP endpoint is needed; this is purely a client-side scoping contract on top of the existing `SearchQueryOptions`.
3. **Deferred:** a future grants-like permission could disable `search_all` entirely for a given MCP client/connection (e.g. a shared daemon serving multiple untrusted agents should expose only `search_local`). Not implemented now — tracked as a follow-up once a concrete multi-tenant/remote-MCP-client use case exists.

## Evaluated Alternatives Ruled Out
- **Single `search` command/tool with a `scope` parameter:** functionally similar, but keeps the unsafe-by-default ambiguity (easy to forget to pass `scope: 'local'`) and gives no distinct name to later gate/restrict independently via tool-level permissions.

## Consequences
- Default CLI/MCP behavior never silently returns hits from a project the caller didn't ask about.
- `dual-interfaces.md`, `cli-and-mcp-interface.md`, `cli-read-only-search.md`, `mcp-server-endpoint.md`, and `hybrid-search-rrf.md` are updated from the one-command/one-tool shape to the two-command/two-tool shape.

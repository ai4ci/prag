## Context
A single search command/tool with an optional `projectId` leaves the local-vs-cross-project default ambiguous: it is easy to forget to pass a scope and silently receive hits from every project on the machine.

## Decision
1. Replace the single `prag search` CLI command with two explicit commands:
   - `prag search-local <query>`: searches exactly one project. The CLI resolves `projectId` from the current working directory (the same git-root-walk already used for branch auto-detection), or takes it from `--project`. This is the default/primary day-to-day command.
   - `prag search-all <query>`: searches across every registered project and **takes no project option at all**. `--branch`/`--limit`/`--mode`/`--json` apply to both.
2. Replace the single `semantic_repository_search` MCP tool with two tools, `search_local` and `search_all`, mirroring the CLI split. Both call the daemon's existing `POST /search`. The scoping contract is strict on both sides:
   - `search_local` **requires** `projectId` in its input schema. The daemon cannot derive it: ADR-011 puts MCP inside the daemon over HTTP/SSE, so there is no caller working directory to walk. The CLI derives it from `cwd`; an MCP client must pass it. A `search_local` call without `projectId` is an error, never a silent widening of scope.
   - `search_all` **does not accept** `projectId`. Unscoped is the whole point of the tool; a project filter here would just be `search_local` under another name.
3. The split is a usability and clarity boundary, not an access-control boundary. `search_local` with an arbitrary `projectId` can read any indexed project, so hiding `search_all` from a caller restricts nothing. Per-caller restriction of query results needs a distinct permission layer — tracked as `issue:search-result-permission-grants.md` and deferred, since all indexed content is local to the user's own machine today.

## Evaluated Alternatives Ruled Out
- **Single `search` command/tool with a `scope` parameter:** functionally similar, but keeps the unsafe-by-default ambiguity (easy to forget to pass `scope: 'local'`) and gives no distinct name to later gate/restrict independently via tool-level permissions.

## Consequences
- Default CLI/MCP behavior never silently returns hits from a project the caller didn't ask about, and the two scopes cannot be confused for one another at the call site.
- `search_local` is reliable over MCP, where no working-directory context exists.
- `dual-interfaces.md`, `cli-and-mcp-interface.md`, `cli-read-only-search.md`, `mcp-server-endpoint.md`, and `hybrid-search-rrf.md` are updated from the one-command/one-tool shape to the two-command/two-tool shape.

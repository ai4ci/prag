## Context
The repository had no toolchain at all: no package manager, no workspace layout, no TypeScript configuration, no test runner, no CI. Every implementation task and the whole test-harness feature (ADR-019) assume one exists.

`prag` depends on three native NAPI modules — `@lancedb/lancedb` (Rust), `onnxruntime-node` (C++, via Transformers.js), and Tree-sitter grammars — so the runtime choice is not purely ergonomic.

## Decision
1. **Package manager and workspaces:** Bun, using Bun workspaces across `packages/core`, `packages/daemon`, `packages/cli`.
2. **Type checking and build:** `tsc`. Bun executes TypeScript directly, so `tsc --noEmit` is the type gate in CI and `tsc` emits declarations for `@prag/core`; Bun's bundler produces the CLI artifact.
3. **Test runner:** `bun test`, which the ADR-019 harness hooks into for setup/teardown. No separate framework.
4. **Runtime target:** Bun for both daemon and CLI, subject to the spike below.
5. **Spike before committing (blocking):** verify that all three native modules load and run under Bun — not merely install. Specifically: open a LanceDB table and run a vector query; run one ONNX embedding pass through Transformers.js; parse a file with each Tree-sitter grammar (TypeScript, Python, R); and confirm `worker_threads` behaves under Bun if ADR-021 lands on a worker pool. Bun's N-API support is good but not complete, and all three of these are exactly the kind of module that exposes the gaps.
6. **Fallback if the spike fails:** Node for `@prag/daemon` (where the native modules live) with Bun retained for the CLI and for `bun test`. The daemon and CLI already communicate only over loopback HTTP (ADR-005), so a split runtime costs nothing architecturally. This fallback is cheap precisely because that boundary already exists.

## Evaluated Alternatives Ruled Out
- **Node + pnpm:** the safest option for native addons and the fallback above, but slower install and test cycles, and no direct TypeScript execution. Chosen against on ergonomics, with the daemon-only fallback retained.
- **Deno:** stricter permissions model would suit an air-gapped tool, but NAPI support for these three modules is the weakest of the three runtimes.
- **Bun's bundler as the type checker:** rejected — Bun strips types without checking them, so a type gate is still needed. `tsc --noEmit` is that gate.

## Consequences
- Install and test cycles are fast, and TypeScript runs without a build step in development.
- The native-addon spike is a prerequisite to the first implementation task; discovering a NAPI gap after the daemon is written would be expensive.
- The CLI artifact is a Bun-produced bundle, which matters for process start time — the interactive budget is 100ms end to end (ADR-005), and interpreter startup is a real fraction of it.

## Amendment 2026-11-03: Node, not Bun

The decision above was never implemented. The project was built on **npm
workspaces, `tsc`, and `tsx` + `node:test` on Node**, which is this ADR's own
§6 fallback, arrived at by default rather than by decision. `bun.lock` and
`package-lock.json` both existed for a time; their drift broke CI on
2026-11-02, which is the concrete cost of leaving the question open.

The blocking spike in §5 was never run. It is now moot for the daemon and is
closed as superseded (`task:toolchain-spike-native-addons.md`).

### What replaces §1-§4

1. **Package manager and workspaces:** npm workspaces. `bun.lock` is deleted.
2. **Type checking and build:** unchanged — `tsc`, via
   `packages/daemon/tsconfig.check.json`, covering all three packages
   including tests.
3. **Test runner:** `node:test` through `tsx`, not `bun test`. The ADR-019
   harness hooks into it, and spawns a real daemon by default
   (`task:test-harness-lifecycle.md`).
4. **Runtime target:** Node for both daemon and CLI. `engines.node` is `>=22`;
   note that Node 24.14.0-24.18.x abort intermittently in their CJS lexer
   (`issue:daemon-suite-flaky-under-parallel-execution.md`), so >= 24.19.0 or
   Node 22 is what developers should run.

### What this costs, measured

CLI start-up, three runs each on this machine: **Bun ~100ms, Node ~190-240ms**
(`prag --version`, which does no work). ADR-005 sets a 100ms end-to-end
interactive budget, so Node exceeds it before the CLI does anything. That is a
real, accepted regression against the budget, not an oversight. Two routes
remain open if it becomes worth paying for:

- Bun for the CLI only, keeping Node for the daemon — the original §6 split.
  The CLI is an HTTP client with no inherent native dependencies, so Bun's
  N-API risk does not apply to it. It currently imports `@prag/core`'s barrel,
  which re-exports `LanceDbSchema` and so pulls LanceDB into its graph; a
  client-safe entry point is a prerequisite and is worth doing regardless.
- Keep a warm daemon and shrink what the CLI loads before its first request.

### Why not Bun for the daemon

Not re-litigated on performance: the daemon is long-lived, so interpreter
start-up is irrelevant to it, and every one of its native modules
(`@lancedb/lancedb`, `onnxruntime-node`, `@kreuzberg/tree-sitter-language-pack`)
is the kind that exposes N-API gaps. Bun would carry all of the risk and
collect none of the benefit. See `issue:no-installation-instructions.md` for
the single-binary question, which is where Bun's remaining appeal lay.

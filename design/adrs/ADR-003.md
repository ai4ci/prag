## Context
Unified multi-language support (including data science layouts like R) requires robust AST tree mapping, while document layout mapping requires layout awareness.

## Decision
Standardize on Tree-sitter (via automated multi-language wrapper registries: `tree-sitter-language-pack`) for programming files and LiteParse for localized binary layouts (PDF/Word). Tree-sitter is used for content-dependent chunking, code chunk whitespace normalisation, and code chunk context management. LiteParse converts rich text directly into cleanly structured local Markdown strings.

## Consequences
Avoids manual tree-walking logic across different languages by outsourcing grammar node configurations to an auto-downloading engine runtime.

## Evaluated Alternatives Ruled Out
### Fixed-Token / Naive Character Chunking (LangChain Standard Splitters)
- **What it is:** Slicing code files strictly by arbitrary token counts or character length rules (e.g. every 512 tokens).
- **Why considered:** Standard fallback method for general-purpose text processing pipelines.
- **Why ruled out:** Completely breaks source code semantics. Blindly slicing code fragments mid-sentence splits variables from execution context or cuts logical scopes (loops, functions) in half, corrupting vector embedding accuracy.
- **The prag Shift:** Replaced by Tree-sitter node boundary parsing, operating as a 'smart ruler' to extract structurally whole, logically independent functional grammar blocks.

### Raw AST Token Vectorization
- **What it is:** Passing raw Abstract Syntax Tree (AST) structural token arrays directly to an embedding layer instead of text code blocks.
- **Why considered:** Attempt to capture purely mathematical syntax trees without relying on text naming variations.
- **Why ruled out:** Standard pre-trained transformer embedding models do not know how to interpret raw abstract token graphs. Pre-trained polyglot code models are trained on human-readable GitHub source code text, relying on contextual patterns, formatting conventions, and descriptive names.
- **The prag Shift:** Tree-sitter is strictly confined to identifying chunking borders. The extracted raw code string is what gets passed to the tokenizer of the local embedding model.

### General-Purpose Agent Orchestration (LangChain)
- **What it is:** Framework for composing LLM chains and tools.
- **Why considered:** Default marketing recommendation for constructing RAG pipelines.
- **Why ruled out:** Engineered for high-level agent orchestration and tool use, but features weak layout parsing defaults. Passing binary layout documents like PDFs or Word files results in naive string extraction that mangles multi-column structures, embedded tables, and footnotes.
- **The prag Shift:** Replaced by LlamaIndex (@llamaindex/liteparse), engineered explicitly for structure-aware parsing, section hierarchy mapping, and native Apache Arrow vector store bindings.
## Amendment 2026-11-03: two document engines, routed by format

This ADR named LiteParse alone for "localized binary layouts (PDF/Word)". On
measurement that is right for PDF and wrong for Word. `@xberg-io/xberg` was
evaluated as a replacement and is adopted alongside, not instead.

### What was measured

Both engines, on this repository's own fixtures
(`test/fixtures/documents/`), which are generated from one `sample.md` so all
three forms should extract to the same prose:

| | LiteParse | xberg |
|---|---|---|
| PDF | 5ms; `#`/`##` headings, `-` bullets, a real table | 12ms; **flat** -- no headings, bullets run together, table flattened to prose, `tables: 0` |
| DOCX | **444ms** (1478ms cold) | **2ms**; same structure |
| HTML | not supported | native, offline |
| Formats | PDF, others via conversion | 141 by extension |
| Install | 33MB | 125MB |

### Decision

**PDF to LiteParse. Every other document format to xberg.**

The split follows from what the formats are, not from benchmark noise. A PDF
does not record that a line is a heading; it records glyphs at coordinates,
and heading level, list structure and table borders have to be *reconstructed*
from that geometry. Reconstructing it is what LiteParse is. Every other format
in `DOCUMENT_FORMATS` states its structure explicitly, and LiteParse reaches
it by rendering to pages and re-deriving what the file already said -- slower
and lossier than reading it.

This ADR's original reasoning -- "LiteParse converts rich text directly into
cleanly structured local Markdown strings" -- holds for PDF and is exactly
what the DOCX measurement contradicts.

### Tree-sitter is unchanged, deliberately

xberg also offers Tree-sitter code intelligence with `contextPath` and byte
spans, which overlaps `core/src/chunker.ts` and looks like a simplification.
It is not taken, because it got **R function names wrong**: `greet <-
function(name)` was reported as `name: "function"`, for both functions in the
spike fixture. R assigns functions to variables and xberg's extractor does not
resolve the assignment. R is the language this ADR was written around, so that
is not a corner case here.

### Consequences

- `DOCUMENT_FORMATS` lives in `@prag/core` and the parsers in `@prag/daemon`:
  three places have to agree about which formats are readable (the dry run's
  promise, the admission gate, the worker) and only one of them can load a
  native addon.
- **Two admission gates had to move.** A document is binary by construction --
  a PDF has NUL bytes in its first 8KB -- so the binary probe refused every
  one before a parser could see it. And `maxFileBytes` is 2MB, sized for
  source files, which refuses most real PDFs; documents get
  `maxDocumentBytes`, 32MB.
- `file_mapping.language` records the document *category* (`pdf`, `docx`),
  never the engine. Which engine handled a format may change, and an index
  that recorded it would need rebuilding when it did.
- **OCR is off in both engines.** It is slow, non-deterministic enough to
  churn chunk hashes between runs, and `feature:local-first-runtime.md`
  forbids reaching for a model that is not already present -- `xberg.doctor()`
  reports several as "first use may download it". A scanned PDF therefore
  yields little text, which is honest; silently taking minutes per file is
  not.
- Install grows by ~158MB of native addons, which feeds
  `issue:no-installation-instructions.md`. xberg ships sibling shared
  libraries (`libonnxruntime`, `libheif`, `libaom`, `libde265`) alongside its
  `.node`, the shape that defeats `bun build --compile`.
- `maxDocumentPages` (500) bounds paginated documents, because page count and
  byte size are only loosely related: a long scanned report fits inside the
  byte cap and still costs minutes and thousands of chunks.

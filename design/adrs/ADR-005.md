## Context
Developers querying codebases from the command line expect immediate sub-second feedback (<30ms). However, computing semantic vector embeddings requires running deep learning models (ONNX runtime), which takes 200ms–800ms to initialize and load weights into memory on each run. Furthermore, LanceDB is an embedded database, meaning concurrent writers and readers across multiple processes can cause file lock contention, schema version skew, and dirty reads during compactions.

## Decision
Adopt a single-writer daemon architecture where all database operations and model execution are centralized in the background daemon, accessible via a local loopback port (`127.0.0.1:<port>`):

1. **Persistent Daemon (`@prag/daemon`):**
   - Keeps ONNX embedding model weights hot in memory (CPU SIMD or GPU).
   - Manages all LanceDB table connections as the sole writer and database handle manager.
   - Listens on a local loopback port (configured in `~/.config/prag/config.json`, default `7724`).
   - Exposes minimal HTTP/JSON endpoints: `/health`, `/search`, `/projects`, `/sync`, `/shutdown`.
2. **Thin Client Wrappers (`@prag/cli` and MCP Server):**
   - Both the short-lived CLI and the Stdio MCP server act as lightweight clients communicating with the daemon over `127.0.0.1:<port>`.
   - **Lazy Startup:** If the daemon is not running when the CLI or MCP server is invoked, the client lazily spawns the daemon in the background (`detached: true`), waits for `/health` readiness, and completes the query.
   - Provides daemon lifecycle control commands: `prag daemon start`, `prag daemon stop`, `prag daemon status`.

## Evaluated Alternatives Ruled Out
- **Direct CLI Database Access via mmap / read-only LanceDB:**
  - *Why considered:* Avoids running a local HTTP server.
  - *Why ruled out:* A CLI doing vector search must convert the query string into a vector. Doing so requires initializing the ONNX model inside the CLI process, incurring a 300ms–800ms penalty on every invocation. Additionally, opening LanceDB tables concurrently with an active background writer risks file locks and version skew.
- **Single Monolithic Binary Executed on Every Call:**
  - *Why considered:* Simplest operational deployment.
  - *Why ruled out:* Severely slow for interactive development; reloading watchers, parsers, and weights on every keystroke/call is unviable.

## Consequences
- CLI queries complete in <15ms because model weights and database handles remain permanently hot.
- Zero database file-locking bugs or write-write conflicts.
- CLI and MCP share an identical thin client protocol.
- Requires local port allocation and loopback security binding (`127.0.0.1` strictly, air-gapped).

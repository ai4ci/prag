## Context
The engine must support rapid, eventually consistent updates under high file churn, branch isolation, and multi-project filtering requirements without running heavy background server daemons.

## Decision
We select LanceDB as the unified data storage engine.

## Consequences
LanceDB operates serverless via zero-copy memory-mapped file operations (mmap), allowing the short-lived CLI tool to boot instantly (<30ms) and interact read-only with database tables. Crucially, it provides native SQL-like scalar predicates, enabling the execution layer to filter out branch constraints (where branch = 'feature') before executing vector arithmetic.

## Evaluated Alternatives Ruled Out
### Naive Text / JSON Files (Vectra)
- **What it is:** A lightweight, local file-based vector index for Node.js saving state into flat text files.
- **Why considered:** Extremely low overhead, zero installation footprint, simple TypeScript interface.
- **Why ruled out:** Fell short on scaling, concurrent access, and branch-aware filtering. High file churn and rapid branch switches require constant mutations; forcing Vectra to update entries required scanning index.json line-by-line via JavaScript. Branch filtering required fetching an excess of vector results and filtering in memory, introducing a massive CPU bottleneck.
- **The prag Shift:** Replaced by LanceDB with transactional, column-oriented Apache Arrow data structures on disk, enabling true SQL-like scalar predicates directly in the storage layer before scoring vector distances.

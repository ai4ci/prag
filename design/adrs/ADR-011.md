## Context
AI coding assistants and agent frameworks (Claude Desktop, Cursor, pi, VS Code) interact with retrieval tools via the Model Context Protocol (MCP). Traditionally, many MCP servers were authored as standalone short-lived processes communicating over standard input/output (`stdio`).

However, `prag` already maintains a long-running background daemon (`@prag/daemon`) bound to a local loopback port (`127.0.0.1:7724`) that hosts the warm ONNX neural embedding models, LanceDB database connections, and in-memory filesystem watchers. Running a separate stdio MCP process would either require:
1. Reloading heavy ONNX embedding models and re-opening database locks in an independent process, or
2. Creating an unnecessary multi-hop proxy layer translating stdio to loopback HTTP.

Modern MCP hosts have native support for remote/local HTTP and Server-Sent Events (SSE) transports.

## Decision
Host the MCP server directly inside the `@prag/daemon` process over HTTP/SSE:
1. **Endpoint:** Expose `/mcp` on the existing loopback daemon port (e.g. `http://127.0.0.1:7724/mcp`), utilizing the official MCP SDK's HTTP/SSE transport.
2. **Co-located Architecture:** The MCP tool handlers (`search_local` and `search_all` per ADR-018, `get_indexing_status`, `watch_uri`, `deny_uri`, `prune_index`) invoke the daemon's internal `SearchEngine`, `IngestionQueue`, and `GrantsManager` services directly in-process with zero network hops or process serialization.
3. **Multi-Client Concurrency:** Multiple editors, terminal agents, and IDE windows can connect to the single running daemon instance concurrently.
4. **Deferred Stdio Bridge:** If a legacy host requiring stdio execution is encountered in the future, a trivial fallback CLI subcommand (`prag mcp`) can be added, but initial implementation targets native HTTP/SSE exclusively.

## Evaluated Alternatives Ruled Out
- **Standalone Stdio MCP Process:**
  - *Why considered:* Initial standard convention for early MCP tools.
  - *Why ruled out:* Forces duplicate database locks or an extra IPC proxy layer; cannot leverage the hot in-process model weights without RPC overhead.

## Consequences
- Zero process churn or duplicate memory consumption.
- Simplifies configuration: agents simply register the MCP server URL (`http://127.0.0.1:7724/mcp`).
- Immediate consistency: MCP tool actions mutate the live daemon state directly.

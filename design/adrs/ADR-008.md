## Context
The retrieval engine needs to handle two distinct update problems:
1. **Rapid local file churn:** Developers in active edit-save-test loops trigger multiple filesystem events per minute. Immediately re-parsing ASTs and computing dense neural embeddings on every event wastes CPU/GPU cycles and causes LanceDB write amplification.
2. **Remote non-local content (Web URIs / Documentation):** Web pages crawled via Firecrawl or HTTP need a mechanism to dictate when they become stale and should be re-crawled, without maintaining a separate scheduler database.

## Decision
Introduce a `validUntil: DateTime` (nullable) column on `file_mapping` functioning as a **freshness lease**:
1. **Local Files (Eventual Consistency Cooldown):**
   - On indexing a file, set `validUntil = now() + cooldown` (e.g. 30–60s).
   - If subsequent change events arrive while `now() < validUntil`, the URI is marked *dirty* in the daemon's in-memory queue, but heavy re-parsing and embedding generation are held back until the lease expires.
   - Once `now() >= validUntil`, the worker re-indexes the latest file content in a single consolidated pass.
2. **Remote Web Content (TTL Rescan Scheduling):**
   - Web URIs use `branch = '$default'` in `branch_mapping`.
   - On crawl, set `validUntil = now() + ttl`, defaulting to `defaults.webCooldownSeconds`
     (86400 = 1 day) — the single source for the web default. A backend that served
     content from a cache or index of unknown age gets a shorter lease (ADR-024).
   - Background re-crawling queries only inspect URIs where `validUntil IS NOT NULL AND validUntil <= now()`.
3. **Static Snapshots / Never Reindex:**
   - Setting `validUntil = null` marks the file version as permanently fresh (e.g. frozen vendor dependencies, lockfiles, archived specifications).

## Evaluated Alternatives Ruled Out
- **Fixed Debounce Only (e.g. 500ms Chokidar debounce):**
  - *Why considered:* Standard for file watchers.
  - *Why ruled out:* A 500ms debounce fires every time the developer pauses for half a second. In a 10-minute coding sprint with 20 saves, it still runs 20 heavy model embedding passes.
- **Separate Web Scheduling Database / Table:**
  - *Why considered:* Keeps local file schema strictly decoupled from web scraping.
  - *Why ruled out:* Adds operational complexity; both local and remote resources fundamentally represent content-addressable document revisions with a freshness window.

## Consequences
- Prevents GPU/CPU thrashing during rapid local editing while guaranteeing eventual consistency in the search index.
- Provides a clean, zero-extra-infrastructure scheduler for remote web crawls.
- Non-git and remote resources use the uniform `$default` branch sentinel.

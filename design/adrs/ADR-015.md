## Context
`chunks_pool.vector` is a fixed-dimension column, but `PRAG_EMBEDDING_MODEL`/`PRAG_EMBEDDING_DEVICE` are user-configurable (`env-and-storage-paths.md`). Changing the model after data already exists risks either a hard dimension-mismatch crash, or worse, silently mixing vectors from two incompatible embedding spaces inside `chunks_pool`, corrupting cosine-similarity ranking with no visible error.

## Decision
1. **Pin on first run:** the first time a data directory is initialized, the daemon writes a sidecar file `~/.local/share/prag/lancedb/.embedding-model.json` (`{ model, dim, pinnedAt }`) from the then-current configuration.
2. **Fail loudly on mismatch:** on every daemon startup, the configured model is compared against the sidecar. On mismatch, the daemon refuses to open `chunks_pool` for writes (read-only `/search` against existing vectors still works) and exits with: "Configured embedding model <X> does not match the model used to build this index (<Y>, pinned on <date>). Run `prag reembed` to migrate, or revert PRAG_EMBEDDING_MODEL to <Y>."
3. **Explicit migration command:** `prag reembed [--model <name>]` calls `POST /reembed` on the daemon, which re-embeds every `chunks_pool.text` row in batches with the new model, sets the affected `projects.status = 'indexing'` for the duration, and atomically updates the sidecar file only on full success. `chunkHash` values are untouched — hashing is structural (ADR-010), not model-dependent — so no re-parsing or re-chunking is required, only new vectors.
4. **No live dual-model support:** out of scope for now; see alternatives.

## Evaluated Alternatives Ruled Out
- **Per-model embedding table (named vectors, as used by e.g. Qdrant's zero-downtime migration pattern):** lets two models' vectors coexist during a gradual cutover and supports rollback, but adds a new table and query-time join that nothing in the accepted feature set currently justifies. Documented here as the natural next step if live multi-model A/B ever becomes a real requirement.
- **Versioned table swap (`chunks_pool_v2` built alongside, then cut over):** reduces downtime during migration at the cost of temporary double disk usage; treated as a possible internal implementation detail of `prag reembed` rather than a contract to commit to now.

## Consequences
- Switching embedding models is a deliberate, visible, one-way operation — never silent, never automatic.
- `prag reembed` may run for a long time on a large multi-project index; it is explicitly user-triggered, not scheduled.
- `env-and-storage-paths.md` gains the sidecar file; `cli-and-mcp-interface.md` gains `prag reembed` / `POST /reembed`; a new task tracks implementation.

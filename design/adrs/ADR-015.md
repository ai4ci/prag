## Context
`vector_pool.vector` is a fixed-dimension column, but `PRAG_EMBEDDING_MODEL`/`PRAG_EMBEDDING_DEVICE` are user-configurable (`env-and-storage-paths.md`). Changing the model after data already exists risks either a hard dimension-mismatch crash, or worse, silently mixing vectors from two incompatible embedding spaces, corrupting cosine-similarity ranking with no visible error.

The vectors are not the only model-dependent artefact. Vectorised-unit boundaries are measured with the active model's tokenizer and capped by `embedding.maxVectorUnitTokens` (ADR-014), so a new model with a different tokenizer or a lower ceiling invalidates the existing windowing too. Re-embedding existing text in place would leave windows sized for the old model and silently truncate against the new one.

## Decision
1. **Pin on first run:** the first time a data directory is initialized, the daemon writes a sidecar file `~/.local/share/prag/lancedb/.embedding-model.json` (`{ model, dim, maxVectorUnitTokens, pinnedAt }`) from the then-current configuration.
2. **Fail closed on mismatch:** on every daemon startup the configured model is compared against the sidecar. On mismatch the daemon serves only `GET /health`, `POST /reembed` and `POST /shutdown` — the first two being the way out of the state and the third keeping `prag daemon stop` working, on the same principle as ADR-016's exempt lifecycle commands. **Every other endpoint, including `POST /search`, is refused** with: "Configured embedding model <X> does not match the model used to build this index (<Y>, pinned on <date>). Run `prag reembed` to rebuild, or revert PRAG_EMBEDDING_MODEL to <Y>."
   Serving reads during a mismatch is not safe: the query is embedded with the new model and compared against old-model vectors. When the two models share a dimension this does not error — it returns confidently ranked nonsense.
3. **Re-embed is a full rebuild, not a vector swap.** `prag reembed [--model <name>]` calls `POST /reembed`, which:
   - drops every content-derived table — `branch_mapping`, `file_mapping`, `chunk_mapping`, `chunks_pool`, `vector_pool` — keeping only the policy and registry tables `grants` and `projects`;
   - writes the new sidecar;
   - sets `projects.status = 'indexing'` and enqueues a full discovery rescan of every registered project onto the normal ingestion queue;
   - returns `{ requeued: <projectCount> }` **immediately**. Dropping tables and seeding the queue is fast; the rebuild itself happens in the background at the ingestion queue's normal rate, under the existing cooldown and batching rules.
4. **Progress, not a long request:** there is no long-lived HTTP call to time out. Progress is observed through the existing `prag status` / `get_indexing_status` surfaces and `projects.status`.
5. **Crash safety:** because the old content tables are gone before the first new vector is written, an interrupted rebuild leaves a *partial* index containing only new-model vectors — never a mix of two embedding spaces. Restarting the daemon resumes from the ingestion queue.
6. **No live dual-model support:** out of scope for now; see alternatives.

## Evaluated Alternatives Ruled Out
- **In-place vector swap (re-embed each stored `text` row):** rejected on three counts — a fixed-width vector column cannot absorb a dimension change, which is the main reason to migrate at all; an interrupted run leaves two embedding spaces mixed in one table; and it preserves vectorised-unit boundaries computed with the old tokenizer, silently reintroducing truncation under the new model.
- **Per-model embedding table (named vectors, as used by e.g. Qdrant's zero-downtime migration pattern):** lets two models' vectors coexist during a gradual cutover and supports rollback, but adds a table and a query-time join that nothing in the accepted feature set currently justifies. Documented here as the natural next step if live multi-model A/B ever becomes a real requirement.
- **Versioned table swap (`chunks_pool_v2` built alongside, then cut over):** avoids the reindexing window at the cost of temporary double disk usage and a second parallel write path; not worth it when the content is all local and re-readable from disk.

## Consequences
- Switching embedding models is a deliberate, visible operation — never silent, never automatic — and the command itself returns instantly.
- The rebuild re-reads and re-parses every watched file, so it costs a full initial index, not just inference. It is explicitly user-triggered, never scheduled.
- `branch_mapping` rows for branches not currently checked out are discarded by the rebuild and re-created the next time those branches are checked out. Nothing is lost that cannot be recovered from the working tree.
- The index is unavailable for search between the mismatch being detected and the rebuild catching up.
- `env-and-storage-paths.md` gains the sidecar; `cli-and-mcp-interface.md` gains `prag reembed` / `POST /reembed`; a task tracks implementation.

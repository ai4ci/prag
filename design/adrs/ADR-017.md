## Context
`chunks_pool` is an intentionally permanent content-addressable dedup cache (ADR-002): a chunk reaching zero live references shouldn't force immediate deletion, because identical content reappearing later (a reverted branch, shared boilerplate across projects) should hit the cache rather than re-pay embedding cost. But disk usage can still grow unbounded without any cleanup path at all.

## Decision
1. **Never automatic, never eager:** no reference-counting column, no scheduled background GC job. `chunks_pool` rows are removed only by an explicit user (or agent) action.
2. **CLI:** `prag prune --gc-chunks`. Plain `prag prune` (no flag) only prunes `branch_mapping` pointers and orphaned `file_mapping`/`chunk_mapping` rows, as already specified in `branch-mapping-and-pruning.md`. The heavier, cache-destroying `chunks_pool` sweep requires the explicit flag.
3. **MCP:** a new tool, `prune_index`, exposing the same capability to agents, with input `{ gcChunks?: boolean }` defaulting to `false` — an agent must explicitly opt in to the `chunks_pool` sweep, mirroring the CLI's explicit-flag requirement.
4. **Mechanics:** `DELETE FROM chunks_pool WHERE chunkHash NOT IN (SELECT chunkHash FROM chunk_mapping)` followed by `table.optimize(cleanup_older_than=...)`, since LanceDB `DELETE` is a soft/versioned operation and disk is only reclaimed after compaction.
5. Both the CLI flag and the MCP tool call the same daemon endpoint, `POST /prune`, whose response is extended to `{ prunedBranches: number, purgedChunks: number }` (already documented) — `purgedChunks` is 0 unless `gcChunks` was set.

## Evaluated Alternatives Ruled Out
- **Scheduled automatic GC (e.g. nightly):** keeps disk tight without user action, but an unprompted background table-scan + compaction can coincide with active indexing and contradicts the project's "the daemon shouldn't surprise you mid-session" posture.
- **Reference-counted eager deletion:** keeps `chunks_pool` minimal continuously, but directly fights the purpose of CAS — a chunk dropping to zero references and later reappearing would force redoing the exact embedding work CAS exists to avoid, and adds write amplification to every `chunk_mapping` mutation.

## Consequences
- Disk usage for `chunks_pool` only shrinks when a user or agent deliberately asks for it, via either interface.
- No write amplification from reference counting during normal ingestion.
- `git-branch-awareness.md`'s GC section and `cli-and-mcp-interface.md` (CLI flag + new MCP tool + `/prune` response shape) are updated.

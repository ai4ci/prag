## Context
The daemon binds strictly to `127.0.0.1`, which stops remote network access but not every local threat: any other local process, or JavaScript running in the user's browser (via a crafted page or DNS-rebinding attack resolving an attacker-controlled hostname to `127.0.0.1`), can send requests to `http://127.0.0.1:7724`. Without authentication, such a request could read indexed code/document content via `/search`, or add/remove `grants` and trigger indexing of arbitrary local paths. This is a known risk class for local dev-tool and MCP servers; standard guidance is Origin validation and/or a bearer token.

## Decision
1. **Shared secret via env var:** The daemon authenticates against `PRAG_API_KEY` (environment variable). If `PRAG_API_KEY` is unset, it defaults to `"guest"` — a convenience default that provides no real security. Set `PRAG_API_KEY` to a unique value on any machine where other local processes or browser-origin network access to the daemon is a concern.
2. **Token file (legacy):** For backward compatibility, when `PRAG_API_KEY` is left at its default `"guest"`, the daemon also writes `~/.local/state/prag/daemon.token` with `0600` permissions as before. Setting `PRAG_API_KEY` to a non-default value skips the file write entirely. Callers should migrate to reading `PRAG_API_KEY` directly; the `daemon.token` file is a compatibility bridge.
3. **Enforcement:** Every HTTP endpoint except `GET /health` requires `Authorization: Bearer <PRAG_API_KEY>`. Missing or mismatched tokens get `401 Unauthorized` with no further processing. `GET /health` stays unauthenticated (needed for the CLI's lazy-spawn liveness poll) and its response body remains limited to metadata — no indexed content or grant data.
4. **Transparent for the CLI:** `@prag/cli` reads `PRAG_API_KEY` directly or falls back to the legacy token file, attaching the header automatically. No user-facing friction for the primary interface.
5. **Explicit for MCP hosts:** MCP clients that support custom headers (Claude Desktop, Cursor, etc.) add `"headers": { "Authorization": "Bearer <PRAG_API_KEY>" }` to their `mcpServers` entry.
6. **`prag daemon token` / `prag daemon rotate-secret`:** These commands continue to work as a convenience — they read/write `daemon.token` when `PRAG_API_KEY` is at its default, otherwise operate on the env var's value.
7. **Origin check (free addition):** Since DNS rebinding can occur even with the correct host header, the daemon additionally rejects any request carrying an `Origin` header that is not a `127.0.0.1`/`localhost` origin, before the token check even runs. `Origin: null` is **rejected**, not allowed: sandboxed iframes and `data:` documents send exactly that, so an attacker can produce it at will. A legitimate CLI or MCP client sends no `Origin` header at all.

## Evaluated Alternatives Ruled Out
- **Rely on `127.0.0.1` binding alone:** Doesn't stop other local processes or DNS-rebinding browser requests from reaching the port.
- **OS-level IPC (Unix domain socket) instead of TCP:** Would remove the loopback-port attack surface for the CLI control plane, but MCP/HTTP+SSE clients (ADR-011) and cross-platform support (Windows) still need a TCP listener, so it doesn't eliminate the need for auth on the HTTP endpoint.
- **Full OAuth/mTLS:** Correct for a networked multi-user service, but disproportionate for a single-user local daemon; adds setup friction with no matching threat it defends against here.

## Consequences
- Any process without `PRAG_API_KEY` set (or filesystem read access to the legacy `daemon.token` file) cannot query or mutate daemon state.
- With the default `"guest"` value, security relies entirely on `127.0.0.1` binding and the Origin check. Set `PRAG_API_KEY` to a unique value on any shared or untrusted machine.
- `PRAG_API_KEY` slots into future access-control plans as the shared-secret primitive for more granular auth schemes.
- MCP client config files now contain a bearer token, at the same trust level as any other local config secret.
- `env-and-storage-paths.md`, `background-worker-queue.md`, and the CLI/MCP interface spec are updated to reflect the auth mechanism.

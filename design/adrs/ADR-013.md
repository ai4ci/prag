## Context
The daemon binds strictly to `127.0.0.1`, which stops remote network access but not every local threat: any other local process, or JavaScript running in the user's browser (via a crafted page or DNS-rebinding attack resolving an attacker-controlled hostname to `127.0.0.1`), can send requests to `http://127.0.0.1:7724`. Without authentication, such a request could read indexed code/document content via `/search`, or add/remove `grants` and trigger indexing of arbitrary local paths. This is a known risk class for local dev-tool and MCP servers; standard guidance is Origin validation and/or a bearer token.

## Decision
1. **Bearer token:** On first startup (if no token exists), the daemon generates a 256-bit random token and persists it at `~/.local/state/prag/daemon.token` with `0600` permissions (owner read/write only), alongside the existing `daemon.pid` and `daemon.port` files.
2. **Enforcement:** Every HTTP endpoint except `GET /health` requires `Authorization: Bearer <token>`. Missing or mismatched tokens get `401 Unauthorized` with no further processing. `GET /health` stays unauthenticated (needed for the CLI's lazy-spawn liveness poll) and its response body remains limited to `{ status, pid, version, uptime, port }` — no indexed content or grant data.
3. **Transparent for the CLI:** `@prag/cli` reads the token file directly (filesystem permissions already scope it to the OS user) and attaches the header automatically. No user-facing friction for the primary interface.
4. **Explicit for MCP hosts:** MCP clients that support custom headers (Claude Desktop, Cursor, etc.) add `"headers": { "Authorization": "Bearer <token>" }` to their `mcpServers` entry. `prag daemon token` prints the current token for copy-paste into such configs.
5. **Stable across restarts:** The token is read from `daemon.token` on startup, not regenerated, so MCP client configs don't go stale on every daemon restart. `prag daemon rotate-secret` regenerates it and invalidates the old one on demand.
6. **Origin check (free addition):** Since DNS rebinding can occur even with the correct host header, the daemon additionally rejects any request carrying a non-empty `Origin` header that isn't `null` or a `127.0.0.1`/`localhost` origin — closing the gap a bearer token alone leaves against a page that could coerce the browser into sending the request, before the token check even runs.

## Evaluated Alternatives Ruled Out
- **Rely on `127.0.0.1` binding alone:** Doesn't stop other local processes or DNS-rebinding browser requests from reaching the port.
- **OS-level IPC (Unix domain socket) instead of TCP:** Would remove the loopback-port attack surface for the CLI control plane, but MCP/HTTP+SSE clients (ADR-011) and cross-platform support (Windows) still need a TCP listener, so it doesn't eliminate the need for auth on the HTTP endpoint.
- **Full OAuth/mTLS:** Correct for a networked multi-user service, but disproportionate for a single-user local daemon; adds setup friction with no matching threat it defends against here.

## Consequences
- Any process without filesystem read access to `daemon.token` cannot query or mutate daemon state.
- MCP client config files now contain a bearer token, at the same trust level as any other local config secret.
- `daemon-http-server-and-lifecycle.md` and the CLI/MCP interface spec are updated to reflect the auth requirement.
